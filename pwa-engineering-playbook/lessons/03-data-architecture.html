Design the data architecture

A reliable PWA gives every kind of state one clear owner. It then moves data through small layers with one-way dependencies.

Dependencies point downward. Components do not know Axios, presigned-upload details, database transactions, or retry rules. Storage code does not import React. Services receive typed values and return domain results. This keeps offline behavior testable without rendering the whole app.

A practical folder shape

src/
  api/                    # one authenticated HTTP client and typed wrappers
  lib/offline-db.ts       # database schema and platform storage helpers
  features/enrollment/
    components/           # screens and status views
    hooks/                # React Query and live IndexedDB adapters
    services/
      enrollment.service.ts        # individual API calls
      offline-enrollment.service.ts # local transactions
      sync.service.ts               # durable workflow
    types/                # domain and persisted record shapes
    utils/                # pure mapping and validation
Persisted types are contractsA TypeScript rename does not migrate records already on users’ devices. Every database schema and persisted enum needs an explicit forward migration or compatibility reader.

Small interfaces keep choices replaceable

type SyncStatus =
  | 'pending' | 'uploading' | 'submitting'
  | 'accepted' | 'failed'

interface OutboxRepository<T> {
  enqueue(value: T): Promise<string>
  claimReady(ownerId: string, now: Date): Promise<T | null>
  markAccepted(localId: string, receipt: ServerReceipt): Promise<void>
  markFailed(localId: string, failure: SyncFailure): Promise<void>
}

interface EnrollmentTransport {
  create(payload: CreateEnrollmentPayload): Promise<ServerReceipt>
}

The repository owns atomic local changes. The transport owns the wire format. The coordinator owns order and recovery. A hook triggers the coordinator and exposes progress. A component only renders the result.

Questions every architecture must answer

  • Which copy is authoritative before sync and after sync?
  • How is data separated between users on a shared origin?
  • What survives reload, logout, expiry, and app update?
  • Which operation must be atomic?
  • How does a screen observe local changes?
  • What does the server return so a retry is safe?
  • When may local data be removed?

Knowledge check

Should a React Query result be copied into a shared store “so every screen can use it”?

Usually no. Let the server-state cache own fetched data and let screens query it by stable keys. Persist only the datasets that have an explicit offline contract, with their own schema and freshness rules.
