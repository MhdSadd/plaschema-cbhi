Security and privacy · 20 minutes

Protect sensitive device data

Offline data is a deliberate copy on a device you do not fully control. Minimize that copy, make its lifetime clear, and assume same-origin JavaScript can reach it.

Draw the threat boundary

Use defense in depth

  • HTTPS and secure service-worker delivery.
  • Strict Content Security Policy with no unsafe inline script in the product app.
  • Trusted Types where practical and output encoding everywhere.
  • Dependency review, lockfile integrity, and minimal third-party scripts.
  • Server validation and authorization for every synchronized operation.
  • Owner/tenant keys in every sensitive local table and every query.
  • Clear local data rules for logout, expiry, reassignment, and device handover.
  • No authenticated API responses in a shared service-worker cache by default.
  • Redacted errors and privacy-aware observability.
  • Documented response for lost devices and stuck sensitive records.

Understand encryption limits

Encrypting IndexedDB may protect against someone reading raw browser profile files. It does not stop XSS if the running app can also obtain the key. A key stored beside the ciphertext is mostly packaging, not a strong confidentiality boundary.

Useful stronger designs need a key not automatically recoverable by arbitrary same-origin JavaScript: for example, a user-supplied passphrase that is never stored, a platform-backed credential flow, or server-assisted key release after authentication. These add recovery and offline-availability tradeoffs. Do not promise “encrypted offline data” without documenting the attacker, key location, unlock flow, rotation, recovery, and logout behavior.

Delete by policy, not hope

Keep accepted device records only as long as required for a durable final acknowledgment or user history promise. Delete their blobs in the same cleanup transaction. Decide what happens to failures older than the supported offline window. A user should be warned before any irreversible discard.

Important limitationBrowser storage is not a secure vault or guaranteed backup. Sensitive or irreplaceable work may require managed devices, shorter offline windows, additional application lock, or a native container.

Knowledge check

Does encrypting IndexedDB with a key stored in localStorage protect against XSS?

No. Malicious same-origin JavaScript can read both the ciphertext and the stored key, or call the app’s decryption code. It may only help against raw-at-rest inspection.
