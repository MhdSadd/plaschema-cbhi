Test, release, observe, and recover

The happy path proves little. A production PWA earns trust by surviving interruption at every boundary.

Test at five layers

Real devices · Android, iOS, installed, browser tab, poor signal
Browser integration · service worker, offline reload, multi-tab, updates
Workflow integration · IndexedDB + coordinator + mocked transport
Storage tests · transactions, migrations, quota errors, cleanup
Pure unit tests · mapping, validation, retry and date calculations

Use a fake IndexedDB for fast workflow tests, but keep browser tests because service-worker lifecycle and storage behavior are browser-owned. Keep a small set of versioned database fixtures from released schemas.

Production release gate

  • HTTPS, manifest, icons, scope, start URL, deep links, and offline navigation verified.
  • Service-worker file revalidates and old cache cleanup is prefix-scoped.
  • Update tested from the oldest supported client, not only a clean profile.
  • Every supported IndexedDB version migrates with real fixtures.
  • API compatibility window and rollback are documented.
  • Storage estimate, quota error, and failed persistence request have UI paths.
  • Outbox failure actions are usable with keyboard and touch.
  • Object-storage CORS and orphan cleanup tested from the deployed origin.
  • No credentials or personal payloads enter logs, cache, docs, or test fixtures.
  • Real device flight-mode/reconnect tests completed.

Observe outcomes, not private content

Useful events include worker version, database version, reference age, queue counts by status, oldest pending age, retry code category, sync duration, update acceptance, migration failure, quota failure, and final report delay. Do not log names, photos, form bodies, tokens, presigned URLs, or unredacted server errors.

A health view for users should show the last complete reference refresh, last complete sync, pending and failed counts, storage warning, app version, and a safe support identifier.

Write recovery before the incident

Never tell users to clear site data before you understand whether it contains unsent work. Prefer a repair release that reads the affected schema. If clearing is unavoidable, explain exactly what will be lost and provide export or assisted recovery where policy permits.

Knowledge check

What is the most valuable test for an idempotent create?

Let the server commit, hide or drop the success response, then retry with the same key. Assert that only one business record exists and the original receipt is returned.
