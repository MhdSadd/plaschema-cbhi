Offline writes · about 25 minutes

Build a durable write queue

The outbox is a local record of work the server has not fully acknowledged. Every transition must survive reload, retry, timeout, and partial success.

Model the workflow as stored states

DraftEditable; not ready to send.
PendingCommitted locally and ready.
UploadingFiles are moving; lease held.
SubmittingMutation request in progress.
AcceptedServer receipt stored.
Report owedFinal batch/device acknowledgement remains.
RemovedSafe local cleanup completed.
FailedNeeds review or explicit retry.

“Syncing” should not exist only in React memory. If the browser closes during upload, the next launch must see enough durable state to recover. Store the stage, attempt count, retry time, lease expiry, uploaded object keys, receipt, and human-safe error.

Idempotency makes uncertainty safe

An idempotency key is a stable identifier for one user intention. Generate it when the draft is created and keep it through edits and retries. The backend stores the result for that key and returns the same logical result when it sees the key again.

A client-generated key alone is not enough. The server must enforce uniqueness and compare the request safely. Decide what happens if the same key arrives with a different payload.

Use a lease, not a permanent lock

Two tabs, an interval, an online event, and a manual Sync button may all start work. Claim one record in a local transaction. Set a lease expiry long enough for the operation. If the process dies, a later coordinator can reclaim it after expiry.

await db.transaction('rw', db.outbox, async () => {
  const current = await db.outbox.get(localId)
  if (!current || current.status !== 'pending') return false
  if (current.retryAt > now || current.leaseUntil > now) return false
  await db.outbox.update(localId, {
    status: 'uploading',
    leaseUntil: addMinutes(now, 5),
  })
  return true
})

Also guard the coordinator in memory so one page does not run duplicate loops. The durable lease handles crashes and competing contexts; the memory guard avoids needless work inside one context.

Retry only what can improve

FailureDefault actionWhy
Network, timeout, 408, 429, 5xxBounded automatic retry with increasing delay and jitter.The request may work later; idempotency protects uncertainty.
401 / expired sessionStop the queue and require authentication.Repeated requests cannot restore authority.
Validation errorFailed; review and edit.The same payload will fail again.
Forbidden assignmentFailed; refresh access and review.Permissions changed.
Duplicate business identityUse server conflict details; do not guess.May be a true duplicate, not an idempotent replay.
File uploaded, create failedKeep object key and retry create.Avoid repeating a successful upload.

Cap automatic attempts. After that, preserve the record and expose Retry, Review/Edit, and carefully confirmed Discard. Never discard merely because the network has been bad for a long time.

Conflicts need a product decision

If offline users edit shared records, send the base revision or ETag. The server should reject a stale edit with the current record and structured conflict details. Then choose one policy per domain: server wins, client wins with permission, field-level merge, duplicate-as-new, or human review. “Last write wins” is still a policy; write down the harm it accepts.

Portable baselineRun synchronization in the foreground on app start, reconnect hints, a modest interval, and a manual button. Background Sync can be an enhancement, not the only path, because it lacks broad browser support.

Coordinator order

  1. Recover expired leases.
  2. Finish any final report already owed.
  3. Load ready records in a stable order.
  4. Claim one record.
  5. Upload missing files and persist each object key.
  6. Submit with the original idempotency key.
  7. Persist the server receipt and durable report marker together.
  8. Continue after non-auth record failures.
  9. Send the final report if any acceptance is owed.
  10. Only then remove accepted records and blobs.

Knowledge check

The server created a record, but the response timed out. What should the client do?

Retry the same logical request with the same idempotency key. The server must return the original result instead of creating a second record.
