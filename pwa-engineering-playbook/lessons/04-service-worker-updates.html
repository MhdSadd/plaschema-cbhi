Ship the shell and safe updates

A service worker is a versioned network proxy with its own lifecycle. Treat each release as a coordinated change between open pages, cached files, local data, and the server.

The lifecycle

Prompt versus automatic activation

Prompt update is the safe default for forms and offline writes. It lets users finish or save before the page reloads. Automatic update can fit read-only content where mixed-version risk is low and reload cannot lose work.

  1. Register the worker at one stable URL and request update checks without a stale HTTP cache.
  2. When a new worker reaches waiting, show a clear, non-blocking prompt.
  3. Disable or defer activation if an unsaved action cannot survive reload.
  4. When the user agrees, message the waiting worker.
  5. The worker calls skipWaiting().
  6. The page receives one controllerchange event and reloads once.
  7. The new worker removes only obsolete, prefixed caches during activation.

The compatibility square

Database migrations must move forward from every supported installed version. APIs should tolerate the supported client window. A new worker should not activate into an old page if it will return incompatible assets. A rollback must understand data already migrated by the failed release.

Prompt update recipe

const registration = await navigator.serviceWorker.register('/sw.js', {
  updateViaCache: 'none',
})

function offerUpdate(worker: ServiceWorker) {
  showPrompt(() => worker.postMessage({ type: 'SKIP_WAITING' }))
}

if (registration.waiting && navigator.serviceWorker.controller) {
  offerUpdate(registration.waiting)
}

registration.addEventListener('updatefound', () => {
  const worker = registration.installing
  worker?.addEventListener('statechange', () => {
    if (worker.state === 'installed' && navigator.serviceWorker.controller) {
      offerUpdate(worker)
    }
  })
})

let reloading = false
navigator.serviceWorker.addEventListener('controllerchange', () => {
  if (reloading) return
  reloading = true
  location.reload()
})

Release checklist

  • Every file required for first paint is in the precache.
  • The worker URL and scope did not move accidentally.
  • The worker response uses revalidation-friendly HTTP headers.
  • Old pages can call the new API during the compatibility window.
  • New pages can read existing local records after migration.
  • The update prompt works with unsaved and queued work.
  • A failed install leaves the old worker usable.
  • Rollback has been tested after the new database version opened.

Knowledge check

Why can “always call skipWaiting during install” be dangerous?

The new worker can begin controlling a page loaded from the old release. Later requests may receive incompatible files or behavior. A prompt and controlled reload keep one page version together.
