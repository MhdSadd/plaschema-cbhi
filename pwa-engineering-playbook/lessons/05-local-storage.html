Build durable local storage

IndexedDB is the durable business-data layer. Design it like a real database: schema, indexes, transactions, migrations, ownership, retention, and failure handling.

Use each browser store for its real job

StoreGood fitMain risk
Memory / component stateTemporary interaction state.Lost on reload.
localStorageSmall non-sensitive preferences and simple session hints.Synchronous, string-only, readable by same-origin JavaScript.
Cache StorageHTTP responses used by a service worker.No domain indexes; stale or cross-user data if policy is careless.

A useful offline-write schema

drafts:      '&ownerUserId, updatedAt'
outbox:      '&localId, ownerUserId, [ownerUserId+status], retryAt'
files:       '&id, ownerUserId, localId, [localId+purpose]'
references:  '&key, ownerUserId, type, serverId, status'
metadata:    '&ownerUserId, syncedAt, accessSignature, schemaVersion'
syncState:   '&ownerUserId, needsReport, updatedAt'

Put the user or tenant boundary in every sensitive record, not only in UI filters. Add indexes for actual queries: owner plus sync status, retry time, file parent, and reference type. Do not index every field “just in case”; indexes increase write and storage cost.

Use transactions around business invariants

Keep transactions short. Do not wait for network requests inside them. Read the necessary local state, write the complete local transition, commit, and perform network work afterward.

Migrations are product releases

  • Never edit an old migration after users may have run it.
  • Add a new monotonically increasing version.
  • Test an empty database and every supported old fixture.
  • Keep persisted state names stable or migrate them explicitly.
  • Handle another open tab blocking the upgrade. Ask it to close or reload.
  • Decide whether rollback code can read the upgraded schema.
  • Do not delete old fields until queued records no longer need them.

Quota, persistence, and retention

Browser storage is best-effort by default. Ask for persistent storage when the device holds important unsent work, but handle refusal. Use navigator.storage.estimate() before accepting large files, catch QuotaExceededError, and show a recovery path.

async function canStore(additionalBytes: number) {
  const estimate = await navigator.storage?.estimate()
  if (!estimate?.quota || estimate.usage === undefined) return true
  return estimate.quota - estimate.usage > additionalBytes * 1.25
}
Persistent does not mean backed upThe user can clear site data, uninstall a browser, lose the device, or suffer profile corruption. For irreplaceable work, shorten the offline window, provide export/recovery where safe, and explain unsynced risk.

Retention rules to decide

  • When accepted records and blobs are removed.
  • Whether logout keeps or wipes the current user’s unsent records.
  • How shared-device users are separated.
  • How stale reference data is replaced.
  • How failed records expire or are escalated.
  • What happens when free space is insufficient.
  • Whether diagnostics may contain personal data.

Knowledge check

Why should “insert outbox record” and “delete draft” share a transaction?

They represent one business transition. If only the delete succeeds, work is lost. If only the insert succeeds, the app may show duplicate active work. One transaction commits both or neither.
