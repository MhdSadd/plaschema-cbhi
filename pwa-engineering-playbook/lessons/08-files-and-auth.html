Large data and identity · 18 minutes

Handle files and offline sessions

Files magnify storage and retry problems. Authentication adds a time limit and an authorization boundary. Model both explicitly.

The file lifecycle

Check type, size, and estimated free space before accepting a file. Store the blob separately from form fields so it can be replaced and cleaned independently. Keep its name, MIME type, size, purpose, owner, and parent local ID. Revoke preview object URLs when the screen releases them.

Keep trust boundaries clear

  1. Ask the authenticated API for an upload instruction containing a short-lived URL and object key.
  2. PUT the exact bytes directly to storage with only the required content headers.
  3. Do not attach the API bearer token to the storage-domain request.
  4. Persist the object key immediately. A retry can skip an upload that already succeeded.
  5. Submit the business record with the keys.
  6. Use server lifecycle rules to remove uploaded objects never attached to a completed record.
Presigned does not mean harmlessRestrict allowed purpose, content type, size, key prefix, expiry, and HTTP method on the server. Configure object-storage CORS for only the deployed app origins and required headers.

Offline authentication is a product policy

Decide whether an unexpired saved session may open offline, for how long, and with which actions. A cached role is not fresh authorization. Every synchronized request must be checked again by the server. If an online identity check returns a real 401 or role mismatch, clear the session and stop the queue. If the network merely fails, preserving local work is safer than treating it as rejection.

Make expiry unsurprising

  • Show when offline access will expire if the user needs to plan field work.
  • Save draft changes before presenting a login screen.
  • Keep unsent records durably separated from the session token.
  • Define whether logout wipes, retains, or transfers unsent work.
  • Handle cross-tab logout and role changes.
  • Never call an authentication retry loop from each outbox record.

Knowledge check

Why persist an uploaded object key before creating the business record?

If create fails or the page closes, the next attempt can reuse the successful upload. This reduces cost and avoids orphaning repeated copies.
