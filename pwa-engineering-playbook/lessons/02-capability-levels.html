Product decision · about 12 minutes

Choose the capability level

Offline is not one setting. Choose the smallest level that satisfies the real field workflow, then state what remains unavailable.

The capability ladder

Level 3 · Offline write
Durable drafts, outbox, files, retries, conflicts, sync
Level 2 · Offline read
Local reference data, freshness, access scope, refresh
Level 1 · App shell
Cached interface, routes, icons, offline explanation
Web foundation
Responsive, secure, accessible, reliable online app

Level 1: app shell

The interface opens and explains what is available. Static routes work. The app may show a cached profile or an offline page, but business data still needs the server. This suits content that is mostly online but must fail gracefully.

Level 2: offline read

Users can read data downloaded earlier. Each dataset needs an owner, freshness date, access signature, replacement rule, and missing-data experience. This works for manuals, catalogues, assignments, maps, or field reference lists.

Level 3: transactional offline write

Users can create or change important records without the server. The app must durably record intent, survive restarts, upload safely, retry without duplicates, expose failures, and resolve conflicts. This is a distributed system running on an unreliable device.

How to choose

  1. Start with the job. Write the step a user must complete during the worst realistic network period.
  2. Name the offline window. Ten minutes, one workday, or several weeks lead to different retention and conflict choices.
  3. Estimate volume. Count records and maximum file size per user per offline window, then add a safety margin.
  4. Classify harm. What happens if data is exposed, lost, duplicated, stale, or submitted twice?
  5. Confirm the server contract. A client cannot invent safe idempotency or conflict handling by itself.
  6. Choose fallbacks. Background Sync is not available in all major browsers; a foreground coordinator is the portable baseline.

Write the offline promise

TemplateAfter [preparation], [user] can [actions] for [offline duration]. The device keeps [data]. When a connection returns, the app [sync behavior]. The following remain unavailable: [limits].

Example: “After signing in and downloading assigned wards, a worker can create enrollments with two files for one day offline. Every save is local first. When the API becomes reachable, records upload one at a time with the same idempotency key. New login and reference refresh remain unavailable offline.”

Common mistakes

  • Choosing libraries before defining the offline promise.
  • Calling a memory cache durable.
  • Promising “full offline” while authentication expires in eight hours.
  • Depending on background browser work without a supported fallback.
  • Ignoring the maximum number and size of files.
  • Leaving conflict behavior for the implementer to invent.

Knowledge check

A catalogue must be viewable offline, but users never change it. Which level is needed?

Level 2. Cache the shell and save a versioned local copy of the catalogue with freshness and replacement rules. A write outbox is unnecessary.
