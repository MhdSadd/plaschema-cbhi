The PWA mental model

A PWA is still a website. Installation changes how it launches. A service worker changes how requests can be handled. Local storage changes what data survives. These are related, but they are not the same feature.

The problem

Teams often say “make it a PWA” as if one switch creates installation, offline pages, durable data, background work, and safe updates. It does not. Treating these as one feature leads to brittle systems: a home-screen icon opens a blank page offline, a cached page shows no data, or a new release deletes work that has not synchronized.

The useful ruleDescribe the exact promise to the user. For example: “After one successful online visit and data download, a signed-in worker can reopen the app, complete a form with two photos, close the browser, and sync later without losing the form.” That sentence is testable.

First visit, returning visit, offline reopening

The first visit must reach the server. The page registers a service worker. The browser downloads and installs it. During installation the worker caches the files required to start the app. On a later navigation, once that worker controls the page, it can answer from Cache Storage even when the network is unavailable.

This works in an ordinary browser tab. Adding the app to a home screen is a convenience and presentation choice. A user who has never loaded the app online has no service worker and no cached shell, so there is nothing to open offline.

Control and scope

A service worker only sees requests under its registered scope. A worker at /field/sw.js normally controls /field/…, not the whole origin. Keep the worker at a stable URL and give cache names a unique product prefix. Otherwise an update may never replace the old worker, or cache cleanup may delete another application’s files on the same origin.

“Online” is only a hintnavigator.onLine reports whether the device appears connected to a network. A captive portal, broken DNS, expired session, or unreachable API can still make the request fail. Let users attempt safe actions and handle the real response.

Common mistakes

  • Testing only the installed standalone window and assuming browser-tab behavior is different.
  • Caching index.html but forgetting a required script, route, font, or icon.
  • Calling a cached shell “offline-first” while every screen still waits for an API response.
  • Caching authenticated API responses without a user boundary, expiry rule, or wipe policy.
  • Changing the worker filename on each release, leaving the old registration behind.
  • Using service-worker installation and PWA installation as if they mean the same event.

Knowledge check

A worker opens the site in Chrome, does not install it, signs in, downloads reference data, closes the tab, and later returns offline. Can the app work?

Yes—if the first visit installed and activated a service worker, the returning page is inside its scope, the complete shell was cached, required business data was saved locally, and the saved session is still allowed offline.
