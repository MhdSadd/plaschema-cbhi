PLASCHEMA case study

The field-worker application is a transactional offline-write PWA. It always saves enrollment work locally, then synchronizes in a durable foreground queue.

The working system

The generated service worker caches static application files and sends navigations to index.html. It does not cache private API responses. Because service-worker installation happens during a normal visit, the app shell can later work offline in a browser tab without being added to the home screen.

Enrollment synchronization

Object keys are saved after upload so retries skip completed stages. The create request keeps the original idempotency key. Accepted records remain hidden but durable until POST /auth/sync succeeds. Only then are records and file blobs removed.

Proven strengths

  • One active owner-scoped draft survives reload and restart.
  • Files are durable IndexedDB blobs, not temporary object URLs.
  • Draft-to-outbox movement is atomic.
  • Idempotency starts at draft creation and survives retry/edit.
  • Expired upload/submission leases recover after interruption.
  • Transient failures use bounded delays; validation failures remain reviewable.
  • Partial batch success still produces a durable final report.
  • Reference streams refresh only when missing, older than 24 hours, or ward access changes.
  • Home statistics combine server totals with only unsent local work, avoiding retained accepted-row double counts.
  • Presigned storage PUTs do not leak the API bearer token.

Deliberate boundaries

ChoiceReason and effect
Foreground sync onlyPortable across target browsers; the app must be open to synchronize.
No API service-worker cachePrivate data stays out of the shared HTTP cache; explicit IndexedDB data has ownership and schema.
Device-local pending listThe PWA handles unsent work; server history belongs to admin.
Unexpired offline sessionSaved identity can continue after transient verification failure, but local expiry stops access.
One-by-one createsEach record has clear idempotency, file stages, receipt, and error.
No push or background syncNot required for the field workflow and avoids uneven platform behavior.

Evidence-based hardening opportunities

  • Complete real-device Android and iOS tests for offline reopen, storage pressure, update, upload CORS, and reconnect.
  • Request persistent storage earlier in the prepared offline workflow, not only when the enrollment screen mounts, and show whether it was granted.
  • Define a stronger shared-device logout/wipe and local-data recovery policy for beneficiary information.
  • Review the JavaScript-accessible token design against a cookie/BFF option and strengthen CSP/XSS controls.
  • Add full service-worker lifecycle and update-prompt browser tests, including the login surface.
  • Verify backend lifecycle cleanup for uploaded objects that never attach to an accepted enrollment.
  • Keep schema migration fixtures as the Dexie database evolves.
The transferable lessonThe strongest part is not a library. It is the sequence of promises: save locally first, persist every irreversible stage, retry with stable identity, report acceptance durably, and delete only after the final obligation succeeds.
